# Captured camera configuration (the chromatrix)

These are the bytes the **ROM's own camera HAL** uploads to the camera
driver, captured on 2026-10-19 from the vendor camera stack running on
**our** kernel. They are *data*: with them, our own imaging server can
configure the ISP and the CPP exactly as the vendor HAL does, without
the ROM, without the vendor libraries, and without the vendor HAL.

## How they were captured

The camera2 stack uploads its configuration in two places, and the
kernel was instrumented (on the `airgap/debug-capture` branch, not on
`master`) to write both out:

| kernel function | ioctl | what it carries |
|---|---|---|
| `msm_isp_proc_cmd()` (`camera_v2/isp/msm_isp_util.c`) | `VIDIOC_MSM_VFE_REG_CFG` | a list of `struct msm_vfe_reg_cfg_cmd` blocks plus a data blob — the ISP's register program |
| `msm_cpp_cfg()` (`camera_v2/pproc/cpp/msm_cpp.c`) | `VIDIOC_MSM_CPP_CFG` | `struct msm_cpp_frame_info_t::cpp_cmd_msg` — the CPP's chromatrix, as a message |

## The files

### `chromatrix_cpp_cmd.bin` — 1064 bytes (266 u32 words)

The chromatrix, exactly as the HAL sends it to the CPP:

```
  word 0 : 0x3e646d63   "cmd>"  (the CAF command-stream magic)
  ...
  word 265: 0xabcdefaa  MSM_CPP_MSG_ID_TRAILER
```

Every capture of it was byte-identical (md5 `9c3162a8264480ddf37f05c9aeb31670`)
across ~600 repetitions in one session, so it is a constant for this
sensor/mode — exactly the kind of thing we want to carry as data.

To send it back:

```c
struct msm_cpp_frame_info_t frame = {
	.frame_id    = 0,
	.inst_id     = 0,
	.client_id  = 0,
	.frame_type = MSM_CPP_FRAME_TYPE,
	.num_strips = 0,
	.strip_info = NULL,
};
frame.cpp_cmd_msg = (void __user *)chromatrix_cpp_cmd;  /* 266 words */
frame.msg_len     = 266;

struct msm_camera_v4l2_ioctl_t ioctl = {
	.len      = sizeof(frame),
	.ioctl_ptr = &frame,
};
ioctl(VIDIOC_MSM_CPP_CFG, &ioctl);
```

on the CPP's device node (`/dev/v4l-subdev17`).

### `chromatrix_isp_cfg.bin` — 2320 bytes

The ISP's half of the same configuration: one `struct msm_vfe_reg_cfg_cmd`
block (`cmd_type=0, cmd_len=0, data_size=2304, data=2`) followed by the
2304-byte data blob the ISP's register program is built from.

### `isp_isp_cfg_*.bin` — the other ISP uploads

The same shape, for every `VIDIOC_MSM_VFE_REG_CFG` the HAL made in one
session — the file name carries the metadata that could not be written
into the file itself (`_n<num_cfg>_l<cmd_len>`):

| file | blocks | data bytes | what it is |
|---|---|---|---|
| `isp_cfg_0_n1_l4.bin` | 1 | 4 | |
| `isp_cfg_11_n1_l8.bin` | 1 | 8 | |
| `isp_cfg_21_n2_l8.bin` | 2 | 8 | |
| `isp_cfg_112_n1_l16.bin` | 1 | 16 | |
| `isp_cfg_1000_n2_l16.bin` | 2 | 16 | |
| `isp_cfg_1003_n1_l36.bin` | 1 | 36 | |
| `isp_cfg_1001_n1_l52.bin` | 1 | 52 | |
| `isp_cfg_22_n1_l128.bin` | 1 | 128 | |
| `isp_cfg_1004_n3_l88.bin` | 3 | 88 | |
| `isp_cfg_20_n2_l180.bin` | 2 | 180 | |
| `isp_cfg_29_n6_l1092.bin` | 6 | 1092 | |
| `isp_cfg_35_n5_l2064.bin` | 5 | 2064 | |
| `isp_cfg_1002_n1_l2304.bin` | 1 | 2304 | the big one — the ISP's register program |

The file name says how many blocks there are (`n`) and how long the data
blob is (`l`); the file itself is the blocks followed by the data blob.

### `sensor/` — the IMX179's mode change

The register arrays the vendor HAL writes to the sensor with
`CFG_WRITE_I2C_ARRAY`, in the order it writes them:

| file | what |
|---|---|
| `00_page_seq_92.bin` | the 92-entry **page sequence** — the sensor's PLL, MIPI and analogue settings, written through the page registers `0xfffd` / `0x0080` / `0xfffc` |
| `01_mode_62.bin` | the 62-entry mode table (the same as `imx179_regs.h`'s `imx179_settings_9`) |
| `02_page_seq_92.bin`, `03_mode_62.bin` | the same two again, as the HAL sends them |
| `04_stream_off.bin` | `0x0100 = 0` |
| `05_config_change_20.bin` | the "config change" array |
| `06_geometry_4.bin` | the geometry (`0x034c`, `0x034e`, `0x0342`, `0x0340`) |
| `07_mode_14.bin` … `13_mode_14.bin` | the mode switches the HAL makes while streaming |
| `08_stream_on.bin` | `0x0100 = 1` — the sensor starts streaming |

Writing only the mode table (as we did before) leaves the sensor silent
on the MIPI link: the page sequence is what makes it transmit at all.
Replayed by `cam/imaging8.c` from
`cam/sensor_config.h` (generated by
`cam/tools/gen-sensor-config.py`).

## Notes for whoever replays these

* The kernel's `msm_cpp_cfg()` copies the message with
  `copy_from_user()` and then **overwrites** `new_frame->cpp_cmd_msg`
  with its own kernel copy. Send the *user* pointer; the driver reads
  the user buffer before replacing the field.
* `msg_len` is in **words** (u32), not bytes.
* The session id has to be the one the driver handed out in its events
  (1 = rear, 2 = front).
